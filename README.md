# Firebird — умный подбор подрядчиков

HackAlem AI · кейс **#79-lite**, владелец задачи — Firebird. [Командный репозиторий](https://github.com/BAITC-Hacks/hack-a9079fb6-team).

По городу, дате, формату, категории и бюджету сервис выбирает **до трёх подрядчиков из предоставленного каталога**. Каждая карточка объясняет выбор проверяемыми фактами и отличиями от соседних карточек. Занятые на дату не попадают в результат. Если вариантов мало или нет, пользователь видит причину и возможное изменение условий.

**Работает без ключей, регистрации, БД и внешних API.** Исходные данные включены в репозиторий. Интернет нужен для установки npm-пакетов; подбор после установки выполняется локально.

## Быстрый запуск с чистого клона

Требования: Git, Node.js **22.12+**, npm. Проверено с Node.js 22.22.2 и npm 10.9.7. Для приватного репозитория нужен доступ команды/организатора; само приложение не требует аккаунтов.

```bash
git clone https://github.com/BAITC-Hacks/hack-a9079fb6-team.git
cd hack-a9079fb6-team
npm i
npm run dev
```

Откройте **http://127.0.0.1:3000**. Нажмите «Популярная категория», «Редкая категория», «Никто не подходит». Копировать `.env.example` и заполнять переменные не требуется. Команды выполняются из корня репозитория.

Если порт занят: `npm run dev -- --port 3001`, затем http://127.0.0.1:3001. Для запуска готовой сборки:

```bash
npm ci
npm run build
npm start
```

## Как устроен подбор

**Next.js App Router + React + TypeScript** обслуживают форму и API; **csv-parse** читает локальный CSV; **Zod** проверяет вход; **Vitest** проверяет ядро/API; **Playwright** проходит пользовательские сценарии в Chromium. Никаких внешних шрифтов или изображений для запуска не нужно.

```text
Форма / демо → POST /api/match → проверка запроса
  → CSV → город + категория → занятость → формат → бюджет → часы → язык
  → детерминированное ранжирование → максимум 3 карточки
  → факты + контраст + цитата → ответ, счётчики отсева, подсказки
```

- CSV: [data/contractors.csv](data/contractors.csv), 66 исходных профилей. Пустой `max_hours` становится `null`; списки и `busy_dates` разбираются по `|`.
- Фильтры строгие: `price_from_kzt <= budget`, `max_hours >= hours`; `null` по часам проходит как неприменимое ограничение. Все заданные условия сохраняются.
- Календарь известен только **23.09.2026–31.12.2026**. За пределами окна API возвращает отдельный `date_out_of_range`, не обещая доступность.
- Ранжирование: лексические совпадения описания с форматом/пожеланием → запас бюджета → совпадение запрошенного языка → доступные часы → `id`. Это прозрачная эвристика по словам, а не семантическая модель. Случайность, текущая дата и внешние ответы на порядок не влияют.
- `funnel` показывает остаток и число исключённых на каждом шаге. Числа отражают последовательный отсев, а не независимую статистику причин.
- Пять технических исходов: `matched`, `partial`, `no_category_in_city`, `none_pass`, `date_out_of_range`. Первые два — пользовательский исход «подобрали».
- Сравнение двух дат применяет один запрос дважды; исчезнувшая карточка помечается `busy` только при наличии второй даты в её `busy_dates`, иначе `ranking`.
- Подсказки пересчитываются по каталогу: ближайшая дата с большим числом кандидатов и минимальное увеличение бюджета, добавляющее кандидатов. Остальные условия остаются прежними. Подсказка появляется только при наличии такого варианта.

## Как проверяются объяснения

Объяснение — **шаблон из фактов**, а не ответ LLM. Оно содержит формат, цену «от», отсутствие отметки занятости на дату и конкретное отличие среди показанных: язык, разницу стартовых цен или длительность. Второе предложение — дословный фрагмент описания с явной атрибуцией «В описании профиля». Рекламное заявление автора не выдаётся за подтверждённую нами гарантию.

Для похожих профилей выбираем различающиеся фактические фрагменты (например, состав музыкантов). Длинная цитата обрезается по границе слова с многоточием. Тесты проверяют принадлежность цитаты исходному описанию, точность числового контраста, различимость без имён, повторяемость и отсутствие мутации данных. Отдельная регрессия покрывает два лайв-бэнда с одинаковыми структурными условиями.

«Совпало N из M» — число выполненных заданных условий, **не вероятность качества и не процент соответствия**. Профиль попадает в выдачу только после прохождения всех фильтров. Исходные `synthetic`, `city_imputed`, `price_imputed` отображаются на карточках. Цена «от» не является окончательной стоимостью; доступность означает отсутствие записи о занятости в предоставленном календаре.

**Jev и другие LLM не используются ни онлайн, ни офлайн.** AI-инструменты использовались при разработке кода и тестов; в работающем продукте нет модельного инференса. Это осознанное ограничение текущей версии, а не заявленная AI-функция.

## API и файлы

- `GET /api/catalog` — значения для полей формы из CSV.
- `POST /api/match` — подбор.
- `POST /api/compare` — `{ "request": <MatchRequest>, "secondDate": "2026-12-19" }`.
- Типы: [lib/contract.ts](lib/contract.ts); описание и примеры: [docs/contract.md](docs/contract.md).
- Ядро: `lib/catalog.ts`, `match.ts`, `ranking.ts`, `explanations.ts`, `suggestions.ts`.
- UI: `app/page.tsx`, `components/match-results.tsx`; серверные обработчики: `app/api/`.

```bash
curl -s http://127.0.0.1:3000/api/match \
  -H 'Content-Type: application/json' \
  -d '{"city":"Алматы","date":"2026-10-15","eventType":"свадьба","category":"Ведущий","budget":1000000}'
```

Пустой подбор — нормальный ответ HTTP 200 с `outcome` и сообщением. Ошибочный запрос — 400; неподходящий Content-Type — 415; тело свыше 8 КБ — 413; межсайтовый POST с чужим Origin — 403. Есть общий лимит 200 запросов в минуту на процесс (429); это защита локального демо, не распределённый production rate limiter. Ответы не кэшируются браузером. В UI есть отмена и таймаут запроса 10 секунд.

## Тесты

```bash
npm test
npm run test:coverage
npm run typecheck
npm run build
npx playwright install chromium
npm run test:e2e
```

E2E сами запускают сервер на порту 3100. На Linux для браузера могут потребоваться системные зависимости: `npx playwright install --with-deps chromium`. Для обычного запуска браузер Playwright не нужен.

- `tests/dod.test.ts`: критерии живой приёмки — детерминизм, разные даты, исходы, пустой ответ словами, до трёх карточек, различимость объяснений, время ответа.
- `tests/core.test.ts`: фильтры, календарь, цитаты, контраст, подсказки и реальные результаты fixtures.
- `tests/api.test.ts`, `tests/http.test.ts`: контракт, валидация, HTTP-ошибки, лимит тела, сравнение дат.
- `e2e/matching.spec.ts`: три демо, повтор, сравнение дат, мобильная ширина и HTTP-время ответа.

Фактический результат последнего прогона и запуск из чистой копии: [docs/verification.md](docs/verification.md).

## Требования, оценка и ограничения

[Исходное ТЗ](docs/task.md) · [Проверка официального Положения](docs/rules-verification.md) · [План и решения](docs/plan.md).

Оценка Firebird: работоспособность **25**, техническая реализация **25**, README/воспроизводимость **25**, ценность **15**, оригинальность и развитие **10**. Приоритет ТЗ — качество объяснений, честные пустые/редкие результаты, скорость, затем UI. По Положению невозможность независимого запуска по инструкции означает недопуск. Требуются подтверждаемые результаты каждого часа. Командная практика — push в `main`; официальная фиксация версии 18:00, внутренние сроки 17:40 (заморозка фич) и 17:55 (финальный push), время Астаны.

Датасет предоставлен организатором и анонимизирован; 13 синтетических профилей уже входят в исходный набор, своих не добавляли. HTML-превью сохранено в `data/` как материал кейса. Публичность репозитория не означает отдельного разрешения переиспользовать данные: права и условия исходного набора остаются у предоставившей стороны.

Использованы сторонние open-source компоненты Next.js, React, TypeScript, Zod, csv-parse, Vitest, Playwright; точные версии в `package-lock.json`, лицензии в установленных пакетах. Собственная функциональность реализована во время хакатона с помощью AI-инструментов разработки.

MVP не бронирует, не связывается с подрядчиками, не обновляет реальные календари и не проверяет истинность рекламных описаний. Следующее развитие: подтверждаемые факты профиля и реальные календари, оценка ранжирования на размеченных заказах, затем необязательный слой семантического поиска с сохранением строгих фильтров и воспроизводимости.
