# Умный подбор подрядчиков — Firebird

HackAlem AI · команда **ҰЛАҒАТ** · кейс **#79-lite** · владелец задачи **Firebird**.

Сервис помогает заказчику выбрать event-подрядчика из существующего каталога: принимает условия мероприятия и возвращает до трёх подходящих карточек с конкретными объяснениями. Главная ценность — объяснить выбор и ограничения, а не просто отсортировать список.

> **Статус: подготовка MVP.** В репозитории находятся исходные данные и каркас документации. Приложение, AI-интеграция, тесты и деплой пока не реализованы. Описанный ниже пайплайн — предложение для реализации; результаты качества и скорости ещё не измерены.

## Задача и границы MVP

Заказчик уже выбрал город и тип мероприятия. Сервис рекомендует подрядчиков из предоставленного каталога, включая площадки с теми же правилами проверки календаря.

**Вход:** город, дата, тип мероприятия, категория подрядчика, бюджет в тенге. Опционально — длительность в часах и язык.

**Выход:** от нуля до трёх карточек. Каждая содержит имя, категорию, город, цену «от» и 1–2 предложения о соответствии конкретному запросу. Объяснение опирается на данные профиля: бюджет, формат, язык, длительность или содержание описания.

Не входят в MVP: бронирование, заявки, уведомления подрядчиков и дообучение модели на 66 профилях. Визуальное оформление вторично по отношению к качеству объяснений.

## Требования к поведению

- Занятый на выбранную дату подрядчик никогда не попадает в выдачу.
- Учитываются город, категория, формат и бюджет, а также заданные язык и длительность.
- Если подходящих меньше трёх, показываем фактическое количество и объясняем ограничение; не дополняем результат неподходящими профилями.
- Одинаковый запрос при неизменных данных и версии ранжирования даёт одинаковый порядок карточек.
- Объяснения конкретны и различаются между подрядчиками. Фразы вроде «отличный выбор для вашего мероприятия» не подходят.
- Не придумываем опыт, свободные даты, скидки, гарантии и другие свойства, которых нет в данных.
- Цена `price_from_kzt` — нижняя граница стоимости за мероприятие, а не подтверждённая итоговая смета.

Пользователь должен различать три исхода:

| Исход | Что показываем |
| --- | --- |
| Подобрали | 1–3 карточки; при неполной выдаче — объяснение причин |
| В городе нет такой категории | Явное сообщение об отсутствии категории в каталоге города |
| Категория есть, но никто не подходит | Причины исключения: занятость, бюджет, формат и другие заданные условия |

### Проверенный состав CSV

| Показатель | Значение |
| --- | ---: |
| Профили / уникальные ID | 66 / 66 |
| Уникальные категории | 17 |
| Алматы / Астана / Зарубежье | 50 / 15 / 1 |
| Полностью синтетические профили | 13 |
| Профили с подставленным городом | 8 |
| Профили с подставленной ценой | 18 |
| Пустое значение `max_hours` | 9 |

Один профиль может относиться к нескольким категориям. Плотные категории: ведущие — 15, фотографы — 12, банкетные залы — 8. Редкие категории по 3 профиля: флорист, декоратор, подарки и сувениры, ведущий церемонии, фото и видеобудки, отель, инструменталист.

| Поля | Значение / особенности чтения |
| --- | --- |
| `id`, `anon_name` | Уникальный ID и вымышленное имя |
| `categories` | Категории; несколько значений разделены `\|` |
| `city` | Город или значение «Зарубежье» |
| `price_from_kzt` | Цена «от», тенге за мероприятие |
| `event_formats`, `languages` | Списки значений, разделённых `\|` |
| `max_hours` | Максимальная длительность присутствия; пустое значение означает `null`, а не ноль |
| `busy_dates` | Занятые даты ISO `YYYY-MM-DD`, разделённые `\|` |
| `description` | Свободное описание на русском |
| `synthetic`, `city_imputed`, `price_imputed` | Строки `True` / `False` в CSV; признаки происхождения данных |

Окно календаря — **23.09.2026–31.12.2026** включительно. По ТЗ отсутствие `max_hours` означает, что работа не привязана к присутствию на площадке. Вне окна календаря нельзя автоматически заявлять свободную дату: до реализации согласовать поведение интерфейса (например, ограничить выбор дат этим окном).

В декабре высокая занятость ожидаема по ТЗ. Пустая выдача может быть правильным результатом. Дополнительные профили разрешены при `synthetic: true`; в демо различаем исходные несинтетические профили, синтетические профили организатора и добавленные командой. Команда пока не добавляла профили.

## Предлагаемый пайплайн

1. **Проверка входа.** Нормализовать запрос, проверить дату, бюджет, опциональную длительность и известные значения категорий/форматов.
2. **Каталог города и категории.** Определить, существует ли исходная группа кандидатов, до остальных фильтров.
3. **Жёсткие фильтры.** Исключить занятых и не соответствующих заданным условиям; сохранить причины исключения для объяснения пустой или неполной выдачи.
4. **Детерминированное ранжирование.** Зафиксировать признаки, веса и разрешение равенства по `id`. Формула ещё не выбрана; не считать самую низкую цену универсальным критерием качества.
5. **Объяснение на фактах.** Сформировать для каждого выбранного профиля набор подтверждённых совпадений. Возможный LLM-слой переформулирует эти факты в 1–2 предложения и не меняет состав или порядок выдачи.
6. **Ответ.** Вернуть до трёх карточек либо понятное состояние отсутствия результатов. При недоступности LLM предлагается резервное объяснение по конкретным фактам профиля.

Это предложение команды, а не дополнительные требования организатора. LLM-провайдер, модель, эмбеддинги, формула ранжирования и способ проверки объяснений — **TODO**. Описания подрядчиков считаются данными, а не инструкциями для модели. Синтетичность и подставленные поля показываются прозрачно и не превращаются автоматически в оценку качества подрядчика.

## Проверка и демо

Definition of Done по ТЗ проверяется вживую. Целевой ориентир времени ответа — до 10 секунд; это пока не измеренный результат.

- [ ] Плотная категория на осеннюю дату: показать реальное ранжирование.
- [ ] Редкая категория: показать доступное количество и причины ограничений.
- [ ] Запрос без результата: понятное сообщение и причины.
- [ ] Отдельно проверить отсутствие категории в городе и отсутствие подходящих среди существующих кандидатов.
- [ ] Подобрать запрос на две даты с изменением доступности: выдача меняется, влияние занятости объяснено.
- [ ] Повторить одинаковый запрос: порядок карточек совпадает.
- [ ] Проверить занятость, границы бюджета, формат, язык, длительность и `null` в `max_hours`.
- [ ] Проверить объяснения без имён: видны специфичные факты каждого выбранного профиля.
- [ ] Убедиться, что возвращено не более трёх профилей и нет неподходящих «для заполнения».
- [ ] Команда может объяснить жюри весь пайплайн и роль AI.

Точные демонстрационные запросы, ожидаемые ID, результаты тестов и замеры задержки добавляются после реализации. Запланированы unit-тесты фильтров/ранжирования, интеграционные тесты полного ответа и E2E основного сценария. По рабочим правилам команды целевое покрытие — не менее 80%; это не отдельное требование ТЗ и не достигнутый показатель.
