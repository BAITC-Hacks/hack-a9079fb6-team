Проверено 23 сентября 2026 года. Этот документ фиксирует требования источников, а не статус реализации.

## Источники

1. [Официальная страница HackAlem AI — вкладка «Положение»](https://edu.astanahub.com/hackathons/df4743f5-c492-415c-b45a-1f13adb78e06?tab=regulations). Полный текст получен из публичного HTML официальной страницы; авторизация и cookies не использовались. Обычный web-reader страницу не прочитал, прямой HTTP-запрос сработал.
2. ТЗ «Умный подбор подрядчиков (#79-lite)», предоставленное пользователем 23.09.2026, включая таблицу оценки. Основные требования отражены в README; оценка ниже перепроверена по оригиналу вложения.

## Главное: README — и баллы, и условие допуска

В ТЗ Firebird **README и воспроизводимость дают 25 из 100 баллов**. Оцениваются понимание устройства проекта, технологии, порядок запуска и основного сценария, возможность воспроизвести и проверить решение по репозиторию.

Общее Положение устанавливает более строгое требование:

- **5.4.15, 5.6.3–5.6.4:** эксперты должны самостоятельно развернуть, запустить и проверить проект. README должен содержать назначение решения, архитектуру, технологии, установку, запуск, зависимости, параметры окружения, системные требования и сценарий проверки.
- **5.4.16, 5.6.5:** невозможность запуска по инструкции означает недопуск к дальнейшему отбору. Дополнительные пояснения и исправления не принимаются.
- **5.6.6:** ключевая функциональность проверяется без личных аккаунтов участников, персональных подписок и закрытых учётных записей. Для внешних API нужны демодоступы, тестовые аккаунты или иной способ проверки.

Практическое решение команды: основной сценарий работает без ключей, БД и сетевых вызовов. Команды `npm install`, `npm test`, `npm run build`, `npm run dev` и три демо-запроса нужно проверить на чистом клоне; описывать только фактически проверенное.

## История разработки и дедлайн

- **5.4.8:** по итогам каждого часа требуется фактический промежуточный результат. Подходят код, прототип, дизайн, архитектура, тестирование, подготовка данных и иные подтверждения прогресса.
- **5.4.9, 5.4.11:** основной рабочий репозиторий — репозиторий команды, созданный организатором через платформу; в нём должна сохраняться подтверждаемая история разработки.
- **5.9.2:** отсутствие подтверждённого результата за любой отчётный час — основание дисквалификации. Также основанием является основная разработка вне назначенного репозитория либо отсутствие подтверждаемой истории.
- **5.4.13–5.4.14:** итоговая версия фиксируется в **18:00**; последующие изменения не учитываются даже на Demo Day. Расписание 23.09.2026 в пункте 3.5: разработка 13:00–18:00.

**Уточнение:** буквального требования «push именно в main каждый час» в прочитанном Положении нет. Ежечасный push реального прогресса в `main` — согласованная стратегия команды для выполнения подтверждённого требования. Дополнительные инструкции организатора из официальных каналов могут вводить детали (пункт 3.4); закрытые сообщения не проверялись.

Заморозка новых функций **17:40** и финальный push **17:55** — внутренние сроки команды, позволяющие успеть к официальным 18:00.

## API, AI и сторонние компоненты

- **5.4.12:** разрешены любые AI-инструменты и агенты для кода, интерфейсов, данных, тестирования, архитектуры и документации. Codex не обязателен, если конкретное ТЗ не требует иного.
- **5.4.12.1:** внешние API, облачные платформы и онлайн-сервисы разрешены при обязательном личном присутствии участников на площадке и работе в назначенном репозитории.
- **5.4.4–5.4.4.2:** использование сторонних библиотек, моделей, данных, шаблонов и иных компонентов раскрывается; лицензии соблюдаются. Заготовленные инструменты допустимы, но основная функциональность решения создаётся во время соревнования.
- ТЗ Firebird прямо разрешает готовые эмбеддинги и LLM через API; дообучение на 66 записях вынесено за рамки задачи.

**Jev:** решение пользователя об отмене Jev сохраняется. Пункт о возможной офлайн-проверке фактов в пересланном плане не является основанием подключать отменённый сервис. Шаблоны должны честно называться шаблонами; нельзя заявлять AI-возможности, которых нет в реализации.

## Обязательная проверка Firebird перед сдачей

1. До трёх карточек с индивидуальными объяснениями по фактам; цена обозначается как «от».
2. Занятые на выбранную дату подрядчики никогда не включаются.
3. Один запрос даёт тот же порядок; проект также обеспечивает одинаковый текст.
4. Пользователь различает подбор, отсутствие категории в городе и отсутствие подходящих по условиям. `partial` — частный случай подбора; `date_out_of_range` — отдельная проверка входа.
5. Если карточек меньше трёх или нет, причина выражена словами.
6. Демонстрируются плотная осенняя категория, редкая категория и пустой результат.
7. На заранее выбранной паре дат выдача меняется из-за занятости, и это видно в интерфейсе. ТЗ не означает, что любые две разные даты обязаны отличаться.
8. Ориентир ответа — до 10 секунд; объяснения различимы после удаления имён; команда может объяснить весь пайплайн.
9. В репозитории есть данные, lock-файл, рабочие команды и проверяемые демо-сценарии. Секретов нет.

## Что не проверено

Не проверены дополнительные объявления в закрытом Telegram-чате и возможные устные уточнения на площадке. Для предметных требований выше использованы предоставленное ТЗ и публичное официальное Положение; отдельного подтверждения организатором текущей реализации пока нет.
